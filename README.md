# SuperKart Sales Forecasting: End-to-End ML Deployment

Forecasts product-store level sales revenue for **SuperKart**, a retail chain
operating supermarkets and food marts across multiple tier cities. Covers the
full path from exploratory data analysis, through six tuned ML models, to a
containerized Flask backend with two independent frontends, deployed on
GitHub Codespaces.

> For a full, chronological log of every change made to this project, see
> [`progress.md`](progress.md).

## 1. Business Context

An accurate sales forecast helps SuperKart plan inventory, procurement, and
regional sales strategy for the upcoming quarter, reducing both stock-out and
overstock risk across its network of stores.

## 2. Objective

Build a predictive model of `Product_Store_Sales_Total` (total revenue
generated by a product at a store) from historical product and store
attributes, and deploy it as a real, callable service:

- A **Flask REST API** backend serving the trained model (online and batch
  inference), with every prediction persisted to a small SQLite file so it
  can be reviewed later.
- A **Web Components** frontend built with native Custom Elements and
  Shadow DOM, no framework, no build step. A four step forecasting workflow
  (mode, data, review, results) sits behind a top navigation bar with
  History, Docs, Help, and Contact pages, addressable directly through the
  URL.
- A second, independent **Streamlit** frontend, single prediction, batch
  prediction, and a history tab, for anyone who specifically needs a
  Streamlit UI rather than (or alongside) the one above. Both frontends are
  thin clients over the same backend and share the same prediction history.
- All three packaged as **Docker containers**, connected over a **Docker
  network**, and run inside a **GitHub Codespace**.

## 3. Data

| File | Description |
|---|---|
| `SuperKart.csv` | Training data, 8,763 product-store records with 12 columns (see data dictionary below). |
| `Batch_Data_SuperKart.csv` | Sample batch-inference input (10 records, already in the engineered feature format the deployed model expects). |

### Data Dictionary

| Column | Description |
|---|---|
| `Product_Id` | Unique product identifier (2-letter prefix + number) |
| `Product_Weight` | Weight of the product |
| `Product_Sugar_Content` | Low Sugar / Regular / No Sugar |
| `Product_Allocated_Area` | Ratio of the product's display area to the store's total display area |
| `Product_Type` | One of 16 broad product categories |
| `Product_MRP` | Maximum retail price |
| `Store_Id` | Unique store identifier |
| `Store_Establishment_Year` | Year the store was established |
| `Store_Size` | High / Medium / Small |
| `Store_Location_City_Type` | Tier 1 / Tier 2 / Tier 3 |
| `Store_Type` | Departmental Store / Supermarket Type1 / Supermarket Type2 / Food Mart |
| `Product_Store_Sales_Total` | Target: total revenue for that product at that store |

## 5. Modeling Approach

- **Feature engineering:** derived `Product_Id_char` (Food/Drink/Non-Consumable,
  from the `Product_Id` prefix), `Store_Age_Years` (from
  `Store_Establishment_Year`), and `Product_Type_Category`
  (Perishables/Non-Perishables, from `Product_Type`). Dropped `Product_Id`,
  `Product_Type`, `Store_Id`, and `Store_Establishment_Year` as superseded
  or redundant.
- **Outlier handling:** IQR-flagged outliers were documented but not removed.
  They represent legitimate high-value observations, and every model built
  here is a tree-based ensemble, which is not sensitive to the scale of
  extreme values.
- **Data split:** 60% train, 20% validation, 20% test. Validation decides
  which model wins, test is only used afterward to report the final
  model's real performance. `GridSearchCV`'s own 5-fold cross-validation
  runs entirely inside the training split and serves a different purpose:
  picking hyperparameters within one model family, not comparing across
  families.
- **Metric of choice:** RMSE (same unit as the target, penalizes large
  forecasting errors, the most relevant behavior for inventory and
  supply-chain risk), tracked alongside MAE, R-squared, Adjusted R-squared,
  and MAPE.
- **Models built:** all six standard tree-based ensemble families: Decision
  Tree, Bagging, Random Forest, AdaBoost, Gradient Boosting, and XGBoost.
  Each runs inside a single `sklearn` `Pipeline` with a shared
  `ColumnTransformer` preprocessing step (`StandardScaler` for numeric
  features, `OneHotEncoder` for categorical features).
- **Hyperparameter tuning:** `GridSearchCV` (5-fold CV, scoring on
  `neg_root_mean_squared_error`) for all six models.
- **Final model:** selected by lowest validation RMSE among all 12
  candidates (baseline and tuned, for each of the 6 families), then
  checked once against the held-out test set. See the notebook's "Model
  Performance Comparison" section for the exact numbers from your own run.
- **Serialization:** the entire winning `Pipeline` (preprocessing and model
  together) is serialized with `joblib` to
  `backend_files/superkart_model.joblib`, so the Flask API only needs to
  call `.predict()` on raw feature inputs.

## 6. Deployment Architecture

```
                          +----------------------------------------+
                          |            GitHub Codespace             |
                          |                                          |
      HTTPS               |   +--------------+                      |
  (forwarded, public) ----+-->|   backend    |                      |
  port 7860               |   |(Flask, :7860)|                      |
        ^                 |   +--------------+                      |
        |                 |                                         |
        |  fetch()        |   +--------------+                      |
        |  from the       |   |  frontend    |                      |
        |  browser        |   | (Nginx,      |                      |
        |                 |   |  :8501)      |                      |
      HTTPS               |   +--------------+                      |
  (forwarded) ------------+---------^                                |
  port 8501               |         | serves index.html, app.js      |
                          +----------------------------------------+
                                     ^
                                     |
                              a browser, outside
                              the Codespace entirely
```

- The **backend** exposes `POST /v1/predict` (single JSON record) and
  `POST /v1/predictbatch` (multipart CSV upload) on port `7860`, served by
  `gunicorn` inside its Docker container, with CORS enabled since the
  browser calls it directly.
- The **Web Components frontend** is a static app served by Nginx on port
  `8501`. Unlike a Python-based frontend, there is no server-side proxying
  of API calls: the browser itself runs `fetch()` against the backend, so
  the backend's URL has to be one the browser can actually reach, not the
  Docker-internal hostname the containers use to find each other. `env.js`
  supplies that URL, regenerated from the `BACKEND_URL` environment
  variable each time the frontend container starts, and a settings control
  in the app's header can override it at any time without rebuilding or
  redeploying anything, which matters most in Codespaces, where the
  forwarded backend URL is only known once that port has been made public.
- The **Streamlit frontend** runs as its own container on port `8502` and
  calls the backend from Python, server side, so it needs no CORS
  workaround and no client-side URL override, `BACKEND_URL` at container
  start (or the sidebar text box at runtime) is enough. It is independent
  of the Web Components app, either can run without the other.
- The **notebook** itself (in its "Inferencing using Flask API" section)
  talks to the backend directly over its public forwarded Codespace URL,
  demonstrating that both frontends and the backend are fully decoupled.
- This full setup (network, all three images, all three containers, a real
  prediction through the container, and a CORS check) is also built and
  torn down once inside the notebook's "Docker Deployment (Local
  Validation)" section, so every Dockerfile is proven to work before ever
  reaching a Codespace.

### Frontend features

The two frontends cover the same ground with different tools. The
Streamlit app (`frontend_streamlit/app.py`) is three tabs: single
prediction, batch prediction from a CSV upload, and a history tab reading
`GET /v1/history`, with a Clear history button wired to `DELETE
/v1/history`. The Web Components app goes further, described below.

Beyond the four step forecasting wizard, the Web Components app has a top navigation bar
with four more destinations, each addressable directly through the URL hash
(`#/history`, `#/docs`, `#/help`, `#/contact`), so any of them can be linked
or bookmarked directly:

- **History**: every prediction the backend has produced, most recent
  first, with the exact input parameters behind each one available on
  request, and a way to clear everything stored.
- **Docs**: the workflow explained end to end, plus the full API reference.
- **Help**: frequently asked questions and a Model Details section
  describing how the deployed model was built, which model families were
  compared, and how the final one performs on the held out test set.
- **Contact**: how to reach the project owner.

None of this history lives only in the browser tab that created it. Every
call to `/v1/predict` or `/v1/predictbatch` is recorded on the backend the
moment it succeeds (see `backend_files/history_store.py`), so the History
page and the sidebar on the wizard both reflect what the API has actually
done, surviving a reload or a different browser entirely. The Batch Upload
step also has a Sample CSV button, downloading a small file in the exact
shape the API expects for anyone starting from scratch.

### Running it locally without Docker

The fastest way to try the app on your own machine is to run the backend
and whichever frontend you want as plain Python processes, no Docker and
no Codespace involved.

```bash
# One-time setup, backend and Streamlit both need their own dependencies,
# the Web Components frontend has none, it is static files
pip install -r backend_files/requirements.txt
pip install -r frontend_streamlit/requirements.txt
```

```bash
# Terminal 1: backend
python backend_files/app.py
# Serves on http://127.0.0.1:7860
```

```bash
# Terminal 2: Web Components frontend, a plain static file server is enough
cd frontend_files
python -m http.server 8501
```

```bash
# Terminal 3 (optional): Streamlit frontend
cd frontend_streamlit
streamlit run app.py --server.port=8502
```

Open `http://localhost:8501` for the Web Components app or
`http://localhost:8502` for the Streamlit one. `frontend_files/env.js`
already defaults to `http://127.0.0.1:7860`, and the Streamlit sidebar
defaults there too, so both work immediately with no environment variable
to set. To point at a different backend later, use the gear icon in the
Web Components header or the sidebar text box in Streamlit, no restart
needed for either. This exact setup is also exercised inside the notebook,
in its "Running the Application Locally (Without Docker)" and "Local Smoke
Test" sections.

### Running it with Docker, locally or in a Codespace

```bash
# 1. Build all three images
docker build -t superkart-backend   ./backend_files
docker build -t superkart-frontend  ./frontend_files
docker build -t superkart-streamlit ./frontend_streamlit

# 2. Create a shared Docker network
docker network create superkart-network

# 3. Run the backend, attached to the network, with a stable hostname
docker run -d --name superkart-backend --network superkart-network -p 7860:7860 superkart-backend

# 4. Run the Web Components frontend, pointed at a backend URL the browser
#    itself can reach (see the note on BACKEND_URL below)
docker run -d --name superkart-frontend --network superkart-network \
  -p 8501:8501 -e BACKEND_URL="http://localhost:7860" superkart-frontend

# 5. Run the Streamlit frontend, on its own port, same backend
docker run -d --name superkart-streamlit --network superkart-network \
  -p 8502:8501 -e BACKEND_URL="http://localhost:7860" superkart-streamlit
```

`BACKEND_URL` above needs a different value in each environment. The
Streamlit container makes its own server-side calls to the backend, so any
reachable address works. The Web Components container's browser-side
`fetch()` calls are pickier, its `BACKEND_URL` has to be an address the
browser itself, not the container, can resolve:
- Docker on your own machine: `http://localhost:7860`, the port published to
  the host, as shown above.
- GitHub Codespaces: the **forwarded URL** for the backend's port 7860, only
  known once that port has been set to **Public** in the Ports tab, so start
  the backend container first, forward and publicize its port, copy that
  URL, then pass it as `BACKEND_URL` when starting either frontend
  container. If the URL needs to change later, the gear icon in the Web
  Components header, or the sidebar text box in Streamlit, updates it
  without restarting anything.

In a GitHub Codespace, set port `7860` (and `8501` and `8502`, to share
both UIs) to **Public** in the Ports tab and copy the forwarded URL(s). Use
the `7860` URL as `model_root_url` in the notebook's inferencing section,
and open the `8501` or `8502` URL in a browser to use one of the apps
directly.

Prediction history lives in `history.db`, a SQLite file created inside the
backend container's own filesystem on first write. That is a deliberate,
zero-configuration default for a project at this scale, not a durability
guarantee: recreating the backend container (a fresh `docker run`, or a
Codespace rebuild) starts with empty history. Mount a volume at the
backend's working directory if history needs to survive that.

### Example API calls

```bash
# Single prediction
curl -X POST "$BACKEND_URL/v1/predict" \
  -H "Content-Type: application/json" \
  -d '{"Product_Weight": 12.66, "Product_Sugar_Content": "Low Sugar", "Product_Allocated_Area": 0.027, "Product_MRP": 117.08, "Store_Size": "Medium", "Store_Location_City_Type": "Tier 2", "Store_Type": "Supermarket Type2", "Product_Id_char": "FD", "Store_Age_Years": 16, "Product_Type_Category": "Non Perishables"}'

# Batch prediction
curl -X POST "$BACKEND_URL/v1/predictbatch" -F "file=@Batch_Data_SuperKart.csv"

# Recent prediction history (both calls above get recorded automatically)
curl "$BACKEND_URL/v1/history?limit=10"

# Clear all recorded history
curl -X DELETE "$BACKEND_URL/v1/history"
```

This project was authored and executed using an isolated virtual environment
(`.venv/`, not committed) with pinned dependency versions matching the

```powershell

```

- `build_notebook.py` programmatically assembles the notebook cell by cell.
  It is the authoring tool used to build and regenerate this project's
  notebook, and is not itself part of the graded deliverable.
- `execute_notebook.py` executes the notebook end to end against the
  `superkart-venv` kernel. By default it skips the handful of cells that
  call the live, Codespace-forwarded backend URL, since no Codespace is
  running at authoring time, those are validated locally instead, in the
  notebook's "Local Smoke Test" and "Docker Deployment" sections. In the
  committed notebook, `model_root_url` has since been pointed at the
  running Codespace described under "Live deployment" above and those
  cells were re-run for real, their outputs in the notebook are actual
  responses from the deployed API, not placeholders.
- Docker is optional for a local notebook run. The Docker validation section
  detects whether Docker is available and skips itself cleanly if not,
  rather than failing the run.

## 8. Key Insights and Recommendations

See the notebook's final "Actionable Insights and Business Recommendations"
section for the full write-up. In brief:

- `Product_MRP` and `Product_Weight` are the dominant drivers of sales revenue.
- Store format (size, city tier, store type) explains a lot of the variation
  in sales, but SuperKart currently has only 4 physical stores, so these
  three attributes largely describe the same 4 outlets rather than three
  independent effects.
- Perishable vs. non-perishable product grouping should inform replenishment
  cadence.
- Across all six model families tested, the tuned boosting and Random Forest
  pipelines generalize best and are recommended for integration into
  SuperKart's quarterly procurement planning, with periodic retraining as
  new sales data arrives.
